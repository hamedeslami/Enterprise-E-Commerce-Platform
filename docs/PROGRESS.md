## Decisions confirmed

- Store model: Single-Vendor.
- Primary database: PostgreSQL 18.
- Environments: local development and Docker Compose.
- API-first backend; frontend is a separate future client.
- Modular Monolith; not microservices.
- Initial market: Iran; default locale `fa-IR`; timezone `Asia/Tehran`; persist instants in UTC.
- Store price and commerce amount unit: whole-integer toman (`long` / PostgreSQL `BIGINT` / JSON integer).
- Identifier strategy: UUIDv7 generated by the application and stored as PostgreSQL `uuid`.
- Runtime/framework baseline: .NET 10 LTS, ASP.NET Core 10 and C# 14.
- ORM/provider baseline: EF Core 10.0.15 and Npgsql EF Core provider 10.0.3.
- Customer password login: either email or mobile number; email requires `EmailConfirmed == true`, mobile requires `PhoneNumberConfirmed == true`.
- Customer SMS OTP: only to an existing, previously verified Customer mobile; OTP login never creates an account.
- Staff authentication: username/password followed by mandatory TOTP; a single-use recovery code is the controlled recovery alternative. Password success alone never creates a normal session.
- Customer and Staff authentication paths enforce explicit persisted `AccountType`.
- Customer normalized email and canonical E.164 mobile uniqueness are database-enforced; Staff username remains unique. Customer username is not a login identifier.
- Access and refresh tokens: separate HttpOnly cookies; refresh token values are stored only as cryptographic hashes; rotation and reuse detection required.
- OTP initial policy: 6 digits, 2-minute expiry, 60-second resend cooldown, 5 failed attempts per challenge, 5 sends/phone/hour and 10 sends/phone/24 hours; configurable.
- OTP challenge and shared per-phone/global SMS quotas are persisted and updated atomically in PostgreSQL. ASP.NET Core per-IP rate limiting and edge/WAF protection complement these controls.
- SMS provider is intentionally not selected yet; provider adapter remains independent.
- Refresh replay policy: strict; a valid consumed-token replay revokes the owning session, with no grace window.
- Initial authorization: server-issued JWT role claims mapped through ASP.NET Core policies; no per-request Identity lookup. The accepted stale-role/session-revocation window is the remaining access-token lifetime (target 5 minutes) plus configured clock skew.
- JWT signing: RSA/RS256, minimum 3072-bit key, unique `kid`, public-key overlap during rotation, and fail-closed production startup.
- Browser topology: `shop.com`, `panel.shop.com`, `api.shop.com`; host-only HttpOnly cookies, Secure in production, SameSite=Lax, exact credentialed CORS allow-list and independent CSRF + Origin checks.
- Staff MFA pre-authentication uses a dedicated five-minute `__Host-staff-mfa` cookie; it does not create a normal session.
- ASP.NET Core antiforgery cookie + JSON request token; frontend keeps request token in memory and sends `X-CSRF-TOKEN`.
- Session policy: Customer 30-day absolute / 7-day idle; Staff 12-hour absolute / 30-minute idle. Customer session listing/revocation UX is defined; IP is not shown.

## Phase 2 implementation progress

- Slice 2A complete and merged in PR #8: explicit `AccountType` (`Customer` / `Staff`) persisted independently of roles, with application validation and a PostgreSQL check constraint. Migration intentionally fails if existing users require classification; no implicit backfill is permitted.
- Slice 2B complete and merged in PR #9: UUIDv7 `AuthSession` and `RefreshToken` persistence, database constraints, partial unique index for one active refresh token per session, and PostgreSQL transaction-based atomic rotation. Rotation uses session-first/token-second locking, constant-time secret verification, database time, conditional token consumption and atomic successor insertion. Valid consumed-token replay revokes only its owning session; wrong-secret attempts do not revoke.
- PostgreSQL integration coverage includes successful rotation, wrong-secret non-revocation, strict replay revocation, concurrent same-token refresh, active-token uniqueness and session expiry boundaries.
- Slice 2C design is documented separately. It defines Customer email/mobile password login, verified-mobile OTP, SuperAdmin-only Staff provisioning/password management, employee MFA enrollment/reset, Staff password + mandatory TOTP/recovery, account-level MFA lockout, identifier normalization/uniqueness, session creation, all-session revocation and transactional SMS outbox/provider failover.
- No authentication endpoints, JWT issuance, login cookies, OTP challenge persistence/outbox worker, Staff MFA enrollment/transaction, TOTP or recovery-code implementation has been added yet. PR #10 remains documentation-only.

## Phase 2 scope

- Identity module and its own DbContext/schema/migrations.
- Customer email/mobile password login and verified-mobile SMS OTP sign-in.
- Staff accounts are provisioned only by SuperAdmin, who sets/resets passwords; employees complete a one-time MFA enrollment invitation and then use username/password + mandatory TOTP or single-use recovery code. Five failed MFA attempts in 15 minutes trigger a 15-minute temporary lockout.
- JWT access + opaque refresh cookies, rotation, reuse detection and session revocation.
- CSRF, Origin, CORS, secure cookies and staff/customer authorization policies.
- OTP challenge lifecycle, per-phone/IP/global quotas, PostgreSQL transactional outbox, primary/secondary provider failover, bounded retries, expiry cleanup, provider circuit breakers and abuse telemetry.
- Actor-generic session management including DELETE /sessions sign-out-all for Customer and Staff.
- Security-focused unit/integration tests.
