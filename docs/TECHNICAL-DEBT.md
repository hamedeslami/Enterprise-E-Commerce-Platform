# Technical Debt and Deferred Decisions Register

**Purpose:** No decision deferred during design or implementation may disappear into chat history. Every deferral must have an ID, a reason, a concrete closure gate, and verification evidence. This register is part of the project delivery contract.

**Rule:** "Decide at production" is not a completion criterion. A row may remain open while its trigger has not been reached, but it must be resolved before the stated gate. Any item that is a production security prerequisite blocks production release until closed and verified. If a deliberate risk is accepted rather than fixed, record the accepting authority, scope, expiry/review date and compensating controls; do not relabel it as completed.

## Accepted design trade-offs (not silently treated as defects)

| ID | Trade-off | Current decision | Revisit trigger |
|---|---|---|---|
| AR-SEC-001 | Stateless access JWT is not instantly revoked when a refresh session is revoked or a role/account change occurs. | Accepted bounded residual validity: remaining access-token lifetime (target 5 minutes) plus configured clock skew. | Revisit if business/security requirements demand immediate staff lockout, immediate role revocation, or immediate account-disable enforcement. Any solution needs explicit availability/cache failure semantics and performance tests. |
| AR-SEC-002 | Strict refresh replay detection can force re-authentication after a successful rotation whose response was lost. | Accepted; no replay grace period. Client single-flight/cross-tab coordination reduces accidental races but is not a security boundary. | Revisit only through an explicit security design review; do not quietly add a grace window. |

## Operating rules

1. Every new deferral must be added here in the same change that introduces it.
2. Every row must have a named phase/release gate and objective evidence. "Later", "when needed" or "at production" alone is invalid.
3. Review this register at the start and end of each phase. Pull forward any item whose trigger is approaching.
4. Do not mark an item complete because a provider was selected; implementation, configuration, tests and operational evidence are required.
5. If an item becomes irrelevant, close it with a short rationale and a reviewable decision rather than deleting its history.
6. Production release is blocked by every open row whose gate is "before production"; a risk exception requires explicit owner approval and documented compensating controls.
7. Keep this register synchronized with ROADMAP.md, PROGRESS.md, SECURITY.md and the relevant module design documents.
